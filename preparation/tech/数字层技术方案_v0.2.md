## 1 架构

### 1.1 数据通路

```
                    ┌─────────────────────┐
                    │  DataSource（可插拔）│
                    ├─────────────────────┤
                    │ RealSerialSource     │  ← SO-101 follower，串口，50Hz
                    │ ReplayFileSource     │  ← 录好的 JSONL 回放，用于期中前独立开发
                    └──────────┬──────────┘
                               ↓ 原始关节读数
                    ┌─────────────────────┐
                    │ Calibrator           │  加零位偏移，夹爪值域换算
                    └──────────┬──────────┘
                               ↓ 实机 actual
                    ┌─────────────────────┐
                    │ ModeScheduler        │  跟随 / 反向 / 无关运动
                    │  + 过渡插值           │  + smoothstep 过渡
                    └──────────┬──────────┘
                               ↓ 数字层 target
                    ┌─────────────────────┐
                    │ Broadcaster          │  30Hz，二进制帧
                    │  + Recorder          │  同时写 JSONL 留档
                    └──────────┬──────────┘
                               ↓ 本机 WebSocket，延迟 < 1ms
                    ┌─────────────────────┐
                    │ 浏览器（全屏）        │  60fps 渲染
                    │  左：数字层           │
                    │  右：代码面板         │
                    │  下：target/actual/delta 数值条 │
                    └─────────────────────┘
```

### 1.2 三个时间尺度

| 环节 | 频率 | 说明 |
|---|---|---|
| 串口读实机 | 约 50Hz | `sync_read` 一次约 20ms |
| 后端广播 | 30Hz | 定频，不跟着串口抖动 |
| 浏览器渲染 | 60fps | 渲染循环里对 30Hz 目标做插值 |
| 偏离模式驻留 | 秒级 | 20 秒到几分钟不等 |

三个尺度分开处理。**30Hz 的数据不要进响应式框架**，每秒 30 次依赖更新会让页面抖。状态数据非响应式直通写进 3D 视口，只在渲染循环里消费。

### 1.3 为什么数据源要可插拔

这是整个方案里最省事的一个决定。

期中之前两条线不联调，但数字层总得能演示。做法是后端支持两种数据源：读串口，或者读录好的关节角文件。期中前线 2 用回放文件跑完整的模式逻辑和界面效果，期末联调时把数据源换成串口，**前端一行都不用改**。

这样一来：

- 「期中前不联调」是真的独立，不是拖到最后一起对接
- 界面效果可以脱离实机单独评估，实机不在手边也能调
- 回放文件本身就是评估素材，同一段数据可以反复看

代价只有一件事：第一格内必须把状态流的接口定死（见 2.1）。

### 1.4 偏离在哪算

放在后端。前端只负责把收到的姿态渲染出来。

理由：模式调度涉及随机序列、驻留时间、过渡进度、开场延迟，这些是有状态的；放前端会让状态分散在两处，日志和回放也难做。后端算完发一个最终姿态，前端保持愚笨，调试时只要看后端日志就能知道此刻是哪个模式。

前端仍然要自己做的只有渲染插值，那是为了把 30Hz 补成 60fps，与模式无关。

## 2 接口

### 2.1 状态流（第一格内定死）

| 字段 | 类型 | 说明 |
|---|---|---|
| `t` | float64 | 后端单调时钟，秒。前端用它丢弃过期帧 |
| `seq` | uint32 | 递增序号，用于检测丢帧 |
| `actual[6]` | float32 | 实机六关节角度，度 |
| `target[6]` | float32 | 数字层六关节角度，度 |
| `mode` | uint8 | 0 跟随 / 1 反向 / 2 无关运动 |
| `blend` | uint8 | 过渡进度 0–255，用于前端做可选的二次平滑 |
| `grip` | float32 | 夹爪 0–100，始终跟随实机 |

关节顺序固定为 `shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper`。单位用度，与 LeRobot 的 `use_degrees=True` 一致。

**字节布局（2026-09-25 定死，两端各有一份代码，改一边必须改另一边）：**

Python 用 `struct.Struct("<dI6f6fBB2xf")`，小端，共 **68 字节**。前端是 `web/src/frame.js` 的 `decodeStateFrame`，后端是 `twin/server/protocol.py`。

| 偏移 | 字节 | 类型 | 字段 |
|---|---|---|---|
| 0 | 8 | float64 | `t` |
| 8 | 4 | uint32 | `seq` |
| 12 | 24 | float32×6 | `actual[0..5]` |
| 36 | 24 | float32×6 | `target[0..5]` |
| 60 | 1 | uint8 | `mode` |
| 61 | 1 | uint8 | `blend` |
| 62 | 2 | — | 填充 |
| 64 | 4 | float32 | `grip` |

三条不能改坏的：

- **格式串写 `<`，不写 `=` 或 `@`。** 后两者走本机对齐、静默插 padding，换台机器就整体错位而没有症状。
- **那 2 字节填充是故意的。** DataView 读 float32 不要求对齐，所以对齐错了不会有任何报错，只会在某天想零拷贝 `new Float32Array(buf, 12, 6)` 时直接抛异常。
- **`t` 必须是 float64。** float32 在 1e6 秒量级只剩约 0.06 秒精度，拿它做丢帧判断会失效。`t` 是后端单调时钟，**暂停时也不停**（暂停冻结的是播放时钟），这样前端丢弃旧帧的规则和延迟统计不会因为暂停而失效。

`actual[5]` 与 `grip` 是同一个夹爪的两种编码，权属要写死：**`actual[5]` 是渲染权威**，`grip` 是派生值、只给界面显示。前端不得拿 `grip` 驱动 gripper 关节——实机电机零位还没核对过。

事件与状态帧**走同一条 socket**，处理函数里先按文本/二进制分流。顺序不能反，文本被喂进 `DataView` 会直接抛异常。

### 2.2 两条通道

| 通道 | 格式 | 用途 |
|---|---|---|
| 状态帧 | **二进制**（ArrayBuffer + DataView） | 30Hz 高频姿态 |
| 事件 | JSON 文本 | 代码面板高亮、状态提示、模式切换通知 |

分开的原因：状态帧每秒 30 条，用 JSON 每条要字符串解析和对象分配，30Hz 下不致命但没必要。事件是低频的，JSON 可读性更好，调试时直接看得到。

**修正（2026-09-25）**：这里原先写"二进制比 JSON 省约九成带宽"，按上面那张字段表算过了，实际只省 3–4 倍（68 字节 vs 约 250 字节）。二进制真正值钱的地方是**没有 JSON 解析和对象分配**（30Hz 下避免 GC 抖动），不是带宽。68 字节 30Hz 在线上一共约 2 KB/s，本机回环等于零。

前端侧记得设 `socket.binaryType = 'arraybuffer'`，默认是 blob，不设的话拿到的是 Blob，读不了字节。

### 2.3 时间戳与乱序

WebSocket 重连之后，旧帧可能后到。**前端按 `t` 丢弃比本地已处理时间更旧的帧**，否则数字层会出现一次回跳。这一条在展厅环境下比在实验室重要得多，因为重连会真的发生。

## 3 技术选型

| 层 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 读硬件 | `lerobot` 的 `SOFollower` 或 `FeetechMotorsBus.sync_read` | 官方 API，不要自己写串口协议 | 无 |
| 后端 | Python + `websockets` 或 `fastapi` + `uvicorn` | 一个文件能起 | 无 |
| 传输 | **本机 WebSocket** | 延迟 <1ms；**不用 HTTP 轮询**，30Hz 轮询会抖 | 无 |
| 前端构建 | **零构建**，`<script type="importmap">` 引 three 与 urdf-loader | 不引 Webpack/Vite，改完刷新即见 | Vite（仅当代码量真的失控） |
| 3D | Three.js + `urdf-loader` | 直接吃 URDF + STL，自带关节树与 `setJointValue` | 见 3.2 |
| 形态 | 素模 + 轻量线框 | STL 只有几何没有贴图，素模是默认结果而非额外投入 | 转 GLB |

### 3.1 可以直接读结构的参考实现

| 项目 | 它能提供什么 |
|---|---|
| `rrzhang139/Synchronized-3D-Robot-Visualization` | Python 后端 + Three.js + WebSocket + URDF，几乎一比一的目标架构 |
| Seeed `reBot Arm B601-DM` web simulator | Node + Three.js **零构建**前端，URDF + STL 加载，关节镜像，还做了「控制锁」和重力补偿。它的前端组织方式可以直接照抄 |
| `robit-man/URDF-Threejs-Modifier` | 在 urdf-loader 基础上补了 **mimic 关节**支持，如果 SO-101 的夹爪是 mimic 关节，去这里找参考 |

### 3.2 urdf-loader 的几个已知限制

官方包是 `urdf-loader`（gkjohnson），当前 0.9.x。加载后可直接操作：

```js
robot.setJointValue('elbow_flex', angleInRadians);
// 或
robot.joints['elbow_flex'].setJointValue(angleInRadians);
```

限制与替代：

- 只支持 prismatic / continuous / revolute / fixed 四种关节类型。SO-101 这个范围内没问题
- **mimic 关节支持要确认。** 如果夹爪在 URDF 里是 mimic，0.9.x 的行为需要实测
- 备选包：`@frmlinn/urdf-loader`（完全重写版，零 GC，提供 Shadow DOM web component，长时间连续渲染下内存更稳）、`@feng3d/urdf-loader`
- 另一条路是先把 URDF + STL 转成 GLB 再加载。文件更小、加载更快、层级保留，但会丢掉关节树元数据，需要自己维护关节名到节点的映射。**不推荐**，除非加载真的慢到影响演示

## 4 数字层：姿态求解

### 4.1 零位标定（最容易做错的一步）

实机零位与 URDF 零位必须一致。仓库提供两套约定：

- `new_calib`：每个关节的虚拟零位在关节范围**中点**
- `old_calib`：零位在机械臂**水平完全伸展**的构型

LeRobot 自己的标定按序列号存在 `~/.cache/huggingface/lerobot/calibration/so101/`。做法：

1. 让实机摆到 URDF 定义的零位姿态
2. 读 6 个关节的原始读数
3. 算出 6 个 offset 并缓存
4. 之后每个循环 `twin_angle = raw + offset`

**这一步做完之前不要碰渲染。** 搞错的话数字层姿态整体偏几十度，动作再流畅也是假的，而且后面所有调试都建在错误的基础上。

### 4.2 夹爪：唯一要手写的模型代码

LeRobot 侧夹爪是 0–100 的线性值，URDF 里夹爪是旋转关节。官方 README 明说这个映射「尚未反映到 URDF 和 MJCF 里」，必须自己做。

```python
# 方向与量程都需要实测确认
gripper_rad = math.radians(
    LO + (HI - LO) * (grip / 100.0)
)
```

**两个待实测的点：**

- **方向**。0 是全开还是全闭，公开资料的写法互相矛盾。以实机为准，掰一次就知道
- **量程**。URDF 里夹爪关节的 limit 上下界是多少，读 URDF 得到

夹爪出错的视觉代价很高：方向反了，数字层的夹爪和实机的夹爪会永远相反，观众看一眼就判定屏幕是假的。

### 4.3 坐标系：Z-UP 与 Y-UP

URDF 沿用 ROS 的 Z 轴向上，Three.js 是 Y 轴向上。直接加载整机会侧躺 90°。解法是**根节点整体旋转**：

```js
robot.rotation.set(-Math.PI / 2, 0, 0);
```

不要逐个网格补旋转，会把模型拆散。

### 4.4 `onComplete` 是假的完成

`onComplete` 在 URDF 的 XML 解析完就触发，此时网格还在加载。要改材质、算包围盒、落地，必须再等 `LoadingManager` 清空。

```js
const manager = new THREE.LoadingManager();
manager.onLoad = () => { /* 此时网格才真正到位 */ };
const loader = new URDFLoader(manager);
loader.load('so101_new_calib.urdf', (robot) => { scene.add(robot); });
```

顺序搞反的症状是：模型加载完但材质没生效，或者包围盒算出 (0,0,0) 导致相机定位全错。

## 5 数字层：三种模式

### 5.1 跟随

`target = actual`，直通。

这是唯一要求"忠实"的模式，也是建立信任的模式。

### 5.2 反向

不要直接对关节角取负。

六个关节里 elbow_flex 这类是单向范围关节，取负会跑到限位之外，数字层会穿模或者僵住。正确做法是**在关节限位区间内做反射**：

```
q' = lo + hi - q          # [lo, hi] 为该关节的 limit 区间
```

这个映射把区间映射回自己，天然不会越界。continuous 关节没有限位，直接 `q' = -q`。

**夹爪不参与反向。** 理由在 5.4。

### 5.3 无关运动（偏离）

素材选择直接决定效果真假。三个候选中有一个明显更好：

| 素材 | 效果 |
|---|---|
| **回放另一段已录的示范轨迹** | 推荐。观众看到的是一个完整、可信的动作，只是不是实机正在做的那一个 |
| 关节限位内的正弦叠加 | 一看就不像有人在操作，容易被判定为抖动或故障 |
| 预设固定姿态序列 + 慢速插值 | 可用作补充，但姿态之间的移动会显得机械 |

判断标准是那个归因问题：观众应该怀疑「是不是有人在操作它」，而不是判断「它坏了」。正弦波做不到前者，只能做到后者。

### 5.4 夹爪始终跟随

反向和无关运动里，夹爪都保持跟随实机。

理由是夹爪的开合直接对应物体的状态。跟着乱动的话，观众会看到数字层的夹爪穿进方块或者方块悬空，那是明确的视觉错误，效果是「假」，不是「偏离」。

### 5.5 模式调度

| 参数 | 默认 | 说明 |
|---|---|---|
| 开场只跟随 | 前 90 秒不偏离 | 先让观众把「它跟着实机走」这个印象建立起来 |
| 跟随驻留 | 20–60 秒随机 | 按时间加权，跟随占总时长的 60–70% |
| 反向驻留 | 3–8 秒 | |
| 无关运动驻留 | 5–12 秒 | |
| 过渡时长 | 0.5–2.0 秒 | 不要线性，用 smoothstep |
| 过渡曲线 | `t*t*(3-2t)` | 两端速度为 0，中间不出现折角 |

**过渡不能瞬间跳变。** 跳变会让观众立刻判定设备故障，作品被降级成技术事故。缓慢漂移让人怀疑自己是不是看错了。

**比例按时间加权，不是按次数。** 一次 60 秒的跟随和一次 3 秒的反向，在观众记忆里的权重完全不同。

所有这些参数都是可调项，默认值只是起点。第一次进教室看过效果之后定。

### 5.6 中间态

模式调度还有一个容易漏的地方：过渡过程中 `mode` 已经变了、姿态还没到位。这段时间数字层和实机是"部分对不上"的状态。

处理方式是把 `blend` 一起发给前端，前端可以据此决定要不要额外做点什么（比如过渡期间不刷新 delta 数值，避免数字条在过渡瞬间剧烈跳动）。

## 6 真实感

### 6.1 判断标准

观众判断"真"的依据是这一句：

> 我看到虚拟那个动了，同时真的那个也动了，而且它们动得一样。

不是材质像不像。所以投入压在延迟和对齐上。

### 6.2 不要过度平滑

STS3215 是磁编码器位置寄存器读数，本身带噪声、死区、回差。**这些缺陷是真实感的来源。**

做法上有三种选择，建议从最简单的开始：

1. **只靠渲染循环的指数插值**（默认）。渲染循环里对目标值做指数逼近，系数用 `k = 1 - exp(-λ*dt)`，λ 不要写成固定系数，因为帧率波动时固定系数不稳定

   ```js
   const dt = clock.getDelta();
   const k = 1 - Math.exp(-15 * dt);
   for (const name in target) {
     const cur = robot.joints[name].jointValue;
     robot.setJointValue(name, cur + (target[name] - cur) * k);
   }
   ```

2. **λ 是这个取舍的唯一旋钮。** λ 小（10）看着顺滑但会抹掉微小残差；λ 大（30）残差保留但大动作能看出阶梯。默认 λ=15，现场调

3. **如果固定 λ 满足不了**（既要抖动又要跟手），再上 One Euro Filter。它是自适应低通：静止时截止频率低、强平滑；快速运动时截止频率升高、几乎不滞后。参数 `min_cutoff ≈ 1.0`、`beta ≈ 0.1`、`d_cutoff = 1.0`。比固定系数的一阶低通多花二十行代码，但没有必要一开始就上

**delta 数值一律不过滤。** 那个数字就是要让它小范围跳。

### 6.3 照实呈现不完美

- 到位后关节仍有微小残差：照实显示
- 夹爪夹住物体时角度不是整数：照实显示
- 读状态偶发延迟：数字层短暂停住，不补间

### 6.4 不要追求照片级

STL 只有几何、没有材质贴图，素模是默认结果。这其实是好事：素模加轻量线框不承诺自己是照片，观众不会拿它去比材质。

可加的低成本项：

- 线框描边，让连杆边界清楚
- 一个接地软阴影（贴图做就行，不需要真实阴影贴图）
- 一个与观众视角接近的默认相机位姿。观众站在教室前面看实体，数字层的默认视角最好接近这个角度，对照才直接。轨道控制保留，观众想转就转

### 6.5 不要跑物理

物理仿真会引入自己的延迟和状态分叉，数字层和实机不一致，而**不一致就是假，比素模更假**。数字层要的是一面镜子，不是一个平行世界。

MuJoCo、`scene.xml`、STS3215 电机参数那一整套对展陈都是多余的。`so101_new_calib.urdf` 加上网格就够。

## 7 代码面板

内容量可以压到很小，但有一条底线：

> **高亮的触发信号必须是真的。**

三联体的说服力来自三层互相印证。如果代码高亮是自己循环的假动画，观众看两分钟就看穿，右侧那一层塌掉，整个结构就不成立了。

最低成本做法：

```python
# 在真实控制循环里发事件，不是定时器
emit("read_joint_state");  state = read()
emit("map_input");         target = schedule(state)
emit("move_joint");        send(target)
emit("render_twin")
```

- 面板保留 5–7 个函数：`read_joint_state` / `map_input` / `mirror` / `schedule_mode` / `move_joint` / `render_twin` / `show_delta`
- 前端订阅事件名，高亮对应行
- **免费且有效的加分项**：把真实关节数值打进代码面板的变量显示，`target = [12.4, 88.1, -45.6, ...]`，数字在跳

### 7.1 代码面板是比对偏离的锚点

数字层偏离时，代码面板上的数值仍然来自实机，不会跟着变。有心的观众把数字层的姿态和代码面板的数值对照，能自己发现不一致是设计好的。

不加任何文字说明。墙上贴一句"本装置会故意偏离"是最廉价的解法，它把装置降级成一个需要说明书的玩笑。自己发现的答案更可信。

## 8 可靠性

没有观众摧残机械臂的极端场景，但下面这些在真实演示里会真的发生。

| 情况 | 处理 |
|---|---|
| `sync_read` 偶发失败 | 重试。LeRobot 的 `num_read_retries` 默认就是 2 |
| 重试仍失败 | **冻结数字层在最后一帧**，界面显示一个低调的状态提示，继续尝试重连 |
| 绝对不要 | 抛异常退出、页面白屏、数字层跳到零位 |
| 观众操作 leader 臂 | Python 端 **500ms 指令看门狗**，超时冻结当前目标，不外推 |
| 单步位移过大 | `max_relative_target`，标量 10.0 或按关节给字典 |
| WebSocket 断开 | 指数退避重连；重连后按 `t` 丢弃旧帧 |
| 浏览器崩溃或刷新 | 后端不依赖前端。观众模式下后端继续按自己的节奏跑，页面回来了接上就是 |

LeRobot 的 `max_relative_target` 既可以给标量，也可以按关节名给字典，例如 shoulder_pan 给 15°、elbow_flex 给 20°。观众操作时的响应速度和安全边界可以分开调。

## 15 实施记录（第二步：后端让它自己动起来）

2026-09-25。代码在 `twin/server/`，跑法见 `twin/README.md`。这一步对应 T2。

**一条命令起两个 listener**：`twin/server/main.py` 同时起静态 HTTP（8000，复用 `tools/serve.py` 那套 Handler）和状态帧 WS（8001，`websockets` 库）。没选「websockets 的 `process_request` 同端口服务静态文件」（那条 API 跟版本绑得紧，静态服务还得自己重写），也没选 aiohttp / fastapi 单端口（要拖一串依赖）。代价是多一个端口，前端从 `location.hostname + :8001` 推导 WS 地址，`?ws=` 可覆盖，`?ws=0` 表示不连后端。

**数据源可插拔按第 1.3 节的意思落地了**：动作库当「实机侧的替身」产生 `actual`，数字层以跟随模式忠实呈现。期末把 `MotionLibrarySource` 换成 `RealSerialSource` 就行，后面几环与前端一行都不用改。`RealSerialSource` 现在只有接口和一条 `NotImplementedError`，实现时要注意的几条（lerobot 的 `sync_read`、读失败重试、500ms 指令看门狗、`max_relative_target`）写在注释里了。

**动作库格式**：`{name, title, note, poses:[{move, hold, ease, joints[6]}]}`，joints 单位度。进第 i 个姿态用它自己的 move 秒（从第 i−1 个插值过去，第 0 个从最后一个插值过去），到位后停 hold 秒；所以每个动作的首尾必须是同一个中性姿态，循环才接得上——`library.py --check` 会把这条查出来。**三个动作都是手编关键帧，不是真机示范数据**，文件里写明了，等线 1 的数据到了再替换。

**夹爪方向实测了**（第 13 节待确认项之二）：URDF **−10° 是闭合、100° 是张开**，与官方 README 的「0 全闭 / 100 全开」方向一致。但实机电机零位仍未核对，所以 `grip` 字段只用于显示，前端不拿它驱动关节。

**抓取姿态是搜出来的，不是估的。** 夹爪的嘴默认在竖直平面里开合（一上一下），而方块躺在地上，两者天然对不上，所以先在 `wrist_roll` 上搜一个能让两颚在水平面里开合的角度，定在 −150°（开合轴的竖直分量只剩 0.06）。在那之上再搜手臂姿态，取 `shoulder_lift 32.5 / elbow_flex 12.5` —— 这组角度下两颚的咬合中点正好落到躺地方块的中心高度。方块取 4cm 边长，位置写死在 `web/src/stage.js` 的 `RED_BLOCK`，**和 `motions/pick_red_block.json` 的抓取姿态是一对，改一处就得改另一处。**

**踩过的坑一：`gripper_frame_link` 不是咬合点。** URDF 里 `gripper_frame_joint` 的 origin 在夹爪末端（−7.9 / −0.2 / −98.1mm），看着正是作者定义的抓取参考点。照着它摆方块，数值上「方块与参考点完全重合」，但截图里方块落在两颚外面 —— 夹爪每次都在方块头顶合拢，现象就是「夹不起来」。**更根本的原因**：动颚的长轴与「`gripper_link` 原点 → TCP」的方向夹角实测约 **94°**，两者几乎垂直。所以「沿 TCP 方向走多远」这个量跟两颚在哪没有关系，用它推出来的任何位置都是巧合。

**踩过的坑二：`gripper_link` 里有两个网格。** 0 是 sts3215 电机，1 是 wrist_roll_follower（定颚在其中）。曾经把 7239 个点（含电机）全当成定颚去量两颚间距，中位数被电机拉偏，算出来最大开口只有 30.6mm —— 而实际开口是 55.6mm。顶点云钩子 `__TWIN_LINK_POINTS__` 现在支持按网格取（第三个参数）；筛定颚的判据是「离动颚 25mm 以内」。

**方块位置最终是扫出来的。** 判据不含任何「哪个轴是开合方向」的假设 —— 前面几版全栽在这上面（用错 link、用包围盒、用错误的轴）。现在的做法：要求方块中心到动颚顶点、到定颚顶点的最近距离都 ≥ 半宽（不穿透），两个距离之和不能比边长还大太多（不悬空），接着沿动颚主轴（PCA 求的长轴）的坐标尽量小（靠颚尖）。动颚主轴实测从 94.6mm（颚尖）到 187.7mm（根端），而 `gripper_link` 原点在 200.8mm 处。

**方块边长也跟着一起定了。** 夹爪全开 90° 时开口 50.5mm，收到 55° 时 32.9mm。方块越大，能放的位置越靠根部 —— 4cm 的方块只能放到主轴 184mm，几乎贴着腕部，因为两颚靠尖端那一侧是张开的，只有收窄的根部才刚好容得下 4cm。所以「位置太靠后」和「夹爪合不拢」是同一个几何约束的两面，把方块改成 3.5cm 一起解决：位置提到主轴 164mm，开口也能从 50.5 收到 32.9（合拢幅度比原来的 11mm 大 58%）。**调整方块尺寸时这两条要一起看，只改位置或只改夹爪角都按不下去。**

**方块怎么被夹起来。** 数字层不跑物理，所以抓放是一个约定：夹爪合到能包住方块的开口（`grip` 角换算成毫米，带滞回 —— 合到 edge+4mm 就抓、张到 edge+8mm 才松），且方块中心确实落在咬合点附近（20mm 内），就把方块挂到 `gripper_frame_link` 底下。用 three 的 `attach` 而不是直接改父节点，世界变换不变，所以看不到它「跳」到夹爪上；挂上之后位置由父节点带，跟着臂走、也跟着腕部自转。松口就放回场景里自由落体，落地停住。**判定用夹爪角而不是等后端发一条「抓到了」**：状态帧是给渲染用的定长二进制，加字段要两端一起改，而开合量本来就能从角度算出来。

**这一组常量必须一起改**：`web/src/stage.js` 的 `RED_BLOCK`、`motions/pick_red_block.json` 的抓取姿态、`web/src/block.js` 的 `GRASP_LOCAL`。改了一处没改另两处，表现就是方块又夹不住或者又重叠。

**暂停与接管是两件正交的事**（第 5 节没写清，这里补上）：暂停管的是「后端播不播」——一条上行 JSON 控制消息，后端冻结播放时钟，前端只反映后端回传的状态、不做本地乐观勾选；接管管的是「本地谁写关节值」——前端状态机 `FOLLOW / OVERRIDE / FROZEN`，粘性，按面板上的「回到跟随」退出。页面连上时会主动上报期望状态（默认 running），后端收到就以它为准；后端在没有客户端且已暂停超过 30 秒时自动恢复。这条不写清，「暂停之后刷新页面」会看起来像坏了。

**自检扩到 32 项**。原有静态与关节轴向之外新增：帧率在 25–35Hz、最大帧间隔 < 150ms、`seq` 零缺号、applied 与 target 同量级（漏转弧度会放大 57 倍）、末端轨迹远大于暂停时的静息抖动（阈值自校准，不写死毫米数）、点真实按钮测暂停、恢复、接管。方块那四条（张着爪不误夹 / 合拢夹住 / 举起跟着离地 / 松口落回）同时守着 `RED_BLOCK.position`、抓取姿态与 `GRASP_LOCAL` 三处，任一处改了没跟上就会红。

写这几条时踩了两个坑，记下来省得再犯：**关节要一次 `evaluate` 设完** —— 分几次设的话中间会插进渲染帧，夹爪可能在「臂已到位、爪还没张开」的那一帧误吸附（开口 5mm 就把方块抓住了）；**等待条件要能证明读到的快照是新的** —— 无条件地「等一帧」会读到上一帧的旧值，曾把开口读成 5.1mm、把方块位置读成动作循环举起它时的高度。无头 SwiftShader 下 600ms 只跑得动 1–2 帧，所以按固定时间 sleep 也不行。另外原来「接管期间状态帧仍在推进」只盯 `elbow_flex`，赶上动作里的 hold 段就误报 `target 变化 0.0°`，改成取全部关节的最大变化。三个假失败源也处理了：CDP 的 `Network.loadingFailed` 会把 WS 断开算成资源加载失败、重连日志不能写 `console.error`、无头下渲染帧率不可靠所以速率断言全部基于 WS 事件时间戳。自检不自起后端（Windows 上 `child.kill()` 杀不掉进程树），连不上会返回 2 并打印确切命令。

**顺带修掉的**：`tools/serve.py` 与后端共用 `server/static.py` 一份实现；静态服务器在客户端提前断开时不再打 traceback（浏览器刷新一次就刷一屏，会把真错误淹掉）；CDP 那套代码抽到 `tools/cdp.mjs`，`selftest.mjs` 与新增的 `tools/probe.mjs` 共用。`probe.mjs` 是这一步的副产品但很值：对着活页面跑一段 JS 打结果，方块位置、夹爪几何、关节雅可比全是靠它量出来的，比截图猜快得多。

## 16 实施记录（抓取姿态推倒重来）

第 14、15 两节记的方块落点全都不成立。后来把夹爪几何完整量了一遍，查出三个根本性错误，之前所有推导都建立在它们上面。

**错误一：`gripper_link` 下的网格顺序认反了。** 遍历出来是 0 = sts3215 电机、1 = wrist_roll_follower（**定颚在这里**）、2 = 动颚（它是 `gripper_link` 的子 link，所以会被 traverse 到）。一直拿 0 当定颚，算出来的是「方块离电机多远」，没有任何意义。这也解释了当时为什么反复得到「两侧接触方向不相反」这种怪结论。

**错误二：两颚是上下开合，不是左右。** `wrist_roll −150` 下，腕件 y 范围 0.0196~0.0695、动颚 −0.031~0.051，一上一下。方块躺在地上根本没法夹：下颚要么插进地面，要么方块被上颚整个盖住 —— 实测 15° 合拢时画面里红色像素占比 **0.00%**。改成 `wrist_roll −60` 之后两颚 y 范围基本重合，变成水平开合。

**错误三：从没检查过夹持空隙的高度。** 这是最要命的一条。两颚之间那条缝的高度随 `shoulder_lift` 线性变化：

```
lift 26° → 中点 y 中位 +28.4mm
lift 28° → +17.5mm
lift 30° →  +6.7mm
lift 34° → −14.4mm
```

方块贴地时中心固定在 12.5mm，所以只有 `lift ≈ 29°` 才对得上。之前一直在 30° 下搜，差着 6mm —— **在那个高度上无论 (x, z) 怎么搜都找不到真正的夹持位置**，搜出来的都是「贴着颚尖的一侧」，看上去就是「方块在夹子外面」。

**判据改了三轮，每一轮都漏了东西**：

| 版本 | 判据 | 漏了什么 |
|---|---|---|
| 1 | 到整团夹爪点云的最近距离 ≈ 半宽 | 被伸出去的颚尖满足，方块实际在夹爪外面 |
| 2 | 分别到动颚、到「定颚」 | 部件认错（见错误一） |
| 3 | 加不穿透，但把方块当半径 half 的**球** | 立方体在角方向能到 half·√3 = 30mm，球判据既误杀又漏判 |
| 4 | 盒体不穿透 + 相对两个面外侧都贴着夹爪点 | 不含部件假设，最终采用 |

测量手段也换过：三维截图被遮挡搞晕，换了好几个机位都看不清；最后靠**三向投影图**（Pillow 把顶点云画出来）才看明白方块和两颚的关系。投影图不撒谎，截图会。

**结论：3.5cm 夹不住。** 换了几种判据、五个肩部角，35mm 方块在这个夹爪贴地时都夹不上（要么穿透，要么只有一侧贴住）。能稳定夹住的是 **2.5cm**，3.0cm 也可以但余量很紧。

最终参数（三处必须一致）：

| 位置 | 值 |
|---|---|
| `web/src/stage.js` `RED_BLOCK` | edge 0.025，position `[0.3820, 0.0125, 0.0060]` |
| `server/motions/pick_red_block.json` | shoulder_lift 28 / elbow_flex 12.5 / wrist_roll −60；夹住 gripper 15、张开 90 |
| `web/src/block.js` `GRASP_LOCAL` | `(-0.0133, -0.0030, 0.0083)` |

抬起方式改成**减小** `shoulder_lift`（28 → 8）加收肘到 26。

这一步新增两个调试钩子：`__TWIN_LOOK_AT__(x, y, z, dist, dx, dy, dz)` 把相机怼到任意点（滚轮推近没用 —— OrbitControls 的缩放绕视口中心走，夹爪在画面角落时推得越近越看不见）；`__TWIN_BLOCK__()` 报出方块的世界坐标、是否 held、父节点（调位置前先看它，否则「改完看不到方块」分不清是没生效还是被夹走了）。

两个操作坑：**probe 的 `stride` 必须给够大** —— 动颚一个网格顶点数在 8.5 万量级，全量导出经 CDP 回传会把 probe 卡死（实测跑了三分多钟没有任何输出，最后被 SIGTERM），二三十抽一就够；**旧后端进程会骗人** —— `pkill -f` 在 Windows 上杀不掉它，新进程因端口占用起不来，页面连的还是旧后端、跑的还是旧动作文件，症状是面板上显示着上一版的关键帧角度。要按端口查 PID 再用 `taskkill //F //PID` 杀掉。

## 17 实施记录（屏幕版式与代码层）

2026-09-26，分支 `dev`。这一轮只动前端，外加后端事件里加两个字段。

### 17.1 版式

屏幕分成两半，中间一道竖线。左半是机械臂的三维像，右半是代码层。
页头一行交代三个体（实体 / 数字层 / 代码），其中"实体"是空的 —— 真机在房间里，
不在屏上。这一条不装饰，它把作品的结构直接写在界面上。

配色只有一条规则：**平时整块屏是单色的，只有数字层偏离实机时出现信号红。**
红色取自场景里那个方块（`0xb8342a`），所以颜色本身是读数，不是装饰。
强调色因此不会因为滥用而失效。

字体三档，各有分工：标题用重衬线（全页只出现一次），正文用窄体无衬线，
凡是数字一律等宽并开 `tabular-nums` —— 30 Hz 刷新的读数如果用比例数字会左右抖。

字号用 `clamp()` 挂在视口宽度上（`--u: clamp(13px, 0.55vw + 6px, 18px)`）。
现场是教室大屏，观众在几米外，13px 是看不见的，所以整套字号比常规后台大一档。

### 17.2 代码层四段

从上到下：模式 / 关节角 / 代码轮转 / 事件。

- **模式**：大字号写出当前模式（跟随 / 反向 / 无关运动），下面一条 `blend` 进度。
  跟随态下整段是单色的，偏离时才转红。
- **关节角**：六个关节各一行，目标角、实际角，以及一条按 URDF 限位归一化的行程尺
  （竖线是零位，细刻度是目标，填充条是实际）。目标与实际同时列出来，
  是因为这个装置的问题就是两者的关系。
- **代码轮转**：三块之间每 14 秒换一次 —— 数据通路、当前动作的真实关键帧、前端渲染循环。
  点标题可以钉住某一块，`?plate=0|1|2` 也能直接钉住。
- **事件**：真实事件的流水（连接状态、动作切换、暂停恢复、接管），不是模拟日志。

### 17.3 高亮必须是真信号

代码面板是观众对齐现实的锚点，所以高亮规则里不许有定时器和随机数。
三块各有一套判据，都只看真实状态：

| 块 | 判据 |
|---|---|
| 数据通路 | 暂停 → 播放时钟；模式 ≠ 跟随 → 模式调度；动作之间的停顿 → 动作库；否则 → 广播 |
| 当前动作 | 拿后端给的真实关键帧逐个比目标角，命中哪一帧就高亮哪一行 |
| 渲染 | 断流 → 冻结；接管 → 面板写值；目标与实际差 > 0.5° → 插值追；否则 → 解码状态帧 |

关键帧那一块值得说一句：一开始想用"目标角有没有停住"去数关键帧，实测不行 ——
动作里每个 `hold` 只有 0.1 s，100 ms 才看一眼会整段漏掉。
改成拿 `motions/*.json` 里的原值直接比对目标角就精确了，
所以后端的事件里要带上 `poses`（见 17.4）。指针只允许往后走一格以内，
否则动作首尾是同一个姿态这个闭合约定会把它刚起步就认成最后一帧。

### 17.4 后端只改了一处：动作事件带关键帧

`server/main.py` 的 `action` 事件多了 `path` / `total` / `poses` 三个字段，
让代码面板显示真实的关键帧，而不是前端抄一份 —— 抄一份就会和动作文件脱节，
而脱节的代码面板恰好破坏了这个装置最要紧的东西。

**68 字节状态帧一个字节没动。** 事件是 JSON，加字段向后兼容，前端对缺字段有兜底。

### 17.5 布局上踩到的坑

- **flex 默认会压缩**。控制台是纵向 flex，事件流用 `flex: 1 1 auto` 抢剩余空间。
  事件攒到十几条之后，容器不够高，**所有**块都按比例被压扁，于是关节角那几行
  直接压到"代码"标题上面去了。要显式给固定段 `flex: 0 0 auto`，只让该滚的那一块缩。
- **键盘可达的滑块**：接管挂在 `input` 事件上，方向键只发 `input` 不发 pointer 事件，
  所以键盘操作也覆盖得到（这条是原有实现，重排时保住了）。
- **抽屉收起不影响自检**：`selftest.mjs` 靠 `#panel button` 的文案找按钮，
  `display: none` 的元素 `.click()` 照样派发事件，所以面板默认收起来也能过。
